# One configured EVM chain per installation
This installation remains locked to Turkchain Mainnet, chain ID1919. Multiple candidate registry records may be saved, but the executing network must match the deployment BLOCKCHAIN_CHAIN_ID. Multi-chain execution is disabled; user/API selection of a different chain and activation of another chain are rejected. Changing an existing installation's environment to reinterpret old balances is rejected.
Use a fresh installation and independent PostgreSQL/Redis/secrets to run another EVM chain. Do not reuse a database with historical rewards on another chain.
## New installation
Clone the repository, install the supported Node/PostgreSQL/Redis/Foundry toolchain, run npm ci, and copy .env.example to a protected .env (0600). Generate independent encryption/session/bootstrap secrets, database role and Redis credentials.
Set APP_ENV, APP_URL, database/Redis endpoints, BLOCKCHAIN_CHAIN_ID and matching hex ID, network identity, HTTPS RPC and optional WSS/fallbacks, explorer, native currency name/symbol/decimals, wallet flags and **WALLETCONNECT_PROJECT_ID**.
Legacy CHAIN_ID/CHAIN_RPC_URL/CHAIN_WSS_URL/CHAIN_EXPLORER_URL and BLOCKCHAIN_WALLETCONNECT_PROJECT_ID remain fallback aliases. WALLETCONNECT_PROJECT_ID takes precedence.
Run prisma generate, prisma migrate deploy, typecheck/lint/tests and build. Configure isolated API/web/worker services with the environment and Nginx/TLS. Bootstrap OWNER and MFA, inspect effective configuration, validate RPC Chain ID, and configure branding/social integrations in administration.
The official-server deployment scripts intentionally validate the mandated /var/www/rewards.turkscan.com paths. On another server provision equivalent services and paths as documented in the service templates; application source does not need changing to select another compatible chain.
## Compatibility and safety
Supported chains must implement Ethereum JSON-RPC, EIP155 transaction domains, EIP712 recovery, compatible Solidity0.8.30 EVM execution and native-value transfers. Configure supported EVM compiler target for chains with older opcode support before deploying contracts. WalletConnect additionally requires a valid project and wallet support for the namespace/chain. RPC probes validate Chain ID on fallback reads; explorer URLs are metadata, not proof of transaction finality.
Amounts are integer native base units with configured decimals, never floating point. Network references partition campaign/ledger/claim/transaction records; chain IDs and EIP712 vault addresses domain-separate signatures.
Claims remain paused with MASTER_PAYOUTS_AUTHORIZED=false and REWARD_CLAIMS_PAUSED=true. No contract deployment/funding is automated as an admin configuration action. Explicit owner approval, contract verification, signer configuration, funding and operational verification are required before any real reward activation.
## Configuration precedence
Deployment environment supplies installation identity and secrets. PostgreSQL stores versioned admin records and branding; encrypted credential references override compatible environment credentials. Central reads apply changes without source edits. Installation identity, port, database, Redis and encryption-key changes require controlled service restart. Never rotate the encryption key without a credential re-encryption procedure.
Protected deployment-level env changes must be made over trusted SSH: acquire the session lock, back up the file into root-only storage, validate a temporary0600 file, atomically replace, reload only Rewards services, verify health and restore the backup if verification fails. There is no HTTP environment-file editor.
